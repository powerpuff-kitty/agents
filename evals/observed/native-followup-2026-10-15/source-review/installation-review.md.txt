## Assessment

If global no-write behavior is required, use the independently verified `python3 -B` invocation or equivalent bytecode suppression and retain that boundary explicitly.

## Findings

### I1. Original partial-selection assertion cannot establish prior-profile preservation; recheck fixes it

Location: `/private/tmp/installation-followup-20261015/exercise.py:29`.

Precondition: run the final different-role installation, then evaluate the original `smaller_different_selection_keeps_prior_profile` expression. `designer` is `target/'designer.md'`, while `target.parent/'agents/designer.md'` is the same file. Comparing their bytes therefore compares the file to itself. It remains true for changed bytes and does not compare the prior mode. `unrelated.exists()` checks presence only.

The original recorded `true` is insufficient evidence for the claimed preservation. This is an exercise assertion defect, not a reproduced installer deletion or overwrite.

Counterevidence: `/private/tmp/installation-followup-recheck-20261015/exercise.py:29` compares the current designer and unrelated hash/mode records to `before`, captured at line 26 before the repeated update and final partial selection; the intervening repeat is itself checked for snapshot equality. It also requires the new quality-engineer profile. My independent replay captures designer/unrelated identity immediately before the different selection and verifies the designer hash, mode and modification time afterwards. All pass. Thus the separate recheck and independent replay resolve this evidence gap; the original exercise should remain recorded with its limitation.

### I2. Plain Python cold dry run writes source caches outside the measured installation subtree

Locations: both `exercise.py:7-8` (`snap` only traverses `target.parent`), `:11-12` (plain `python3` subprocess); `source/scripts/install.py:13` (imports build), `:98` (compiles profiles before checking dry-run), `:125` (correctly avoids applying targets on dry-run).

Preconditions: writable source copy with no `__pycache__`, normal Python bytecode generation enabled, then execute the exercise's installer command shape:

```sh
python3 scripts/install.py --agent designer --target /disposable/installed/agents --dry-run
```

Independent reproduction on Python 3.14 creates these four source nodes while preserving the complete installation subtree:

```text
scripts/__pycache__
scripts/__pycache__/build.cpython-314.pyc
adapters/opencode/__pycache__
adapters/opencode/__pycache__/render.cpython-314.pyc
```

Both retained original source directories also contain those two bytecode files. The originals' `dry_run_no_writes` snapshot cannot see them because it only measures `installed/` files, and cannot detect added empty directories, timestamps, transient writes or same-byte rewrites. Therefore its boolean establishes a narrower file-content/mode result, not a global absence of writes.

Counterevidence: the installer source plans all target changes and calls `apply_target` only when `dry_run` is false. My replay verifies no directory/file inventory, content, mode, modification-time or change-time differences in the installation subtree during the first dry run. A separate cold dry run with `python3 -B` and a nonexistent installation destination passes with no such differences anywhere in the complete bounded reproduction tree, including source. This is the concrete verified command variant for a strict no-write exercise.

## Limits and completion boundary

No actual host configuration, existing owner profile directory, provider credential, native host, inference, live service or network was used. Every subprocess installer target is explicit and under a disposable reproduction directory. This verifies local installer behavior for the supplied role-update cases, not native profile/command loading or model outcomes; canonical behavioral coverage remains unchanged. No universal crash/concurrency/rollback guarantee follows from these exercises. Snapshots omit access times and cannot prove absence of transient or outside-tree writes; bytecode behavior is reported explicitly rather than hidden by an installation-only snapshot. No installer target-safety blocker remains for the tested cases; the global no-write wording requires the invocation/boundary qualification described above.
