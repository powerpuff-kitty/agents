# Native recovery and delivery assessment

This is a scenario review for iOS and Android, not an implemented app change. No app source, target revision, stack, project configuration, supported OS/device range, SDK, backend contract or runnable target was supplied. No toolchain/device discovery, SDK install, build, test, signing or distribution was attempted. The precise implementation blocker is the absent receiving app and accepting-boundary contract; a scenario-only report is the available deliverable.

The accepted requirements are to preserve an acknowledged saved draft, avoid duplicate accepted submissions, and expose pending/retry/recovery status without inventing server guarantees. An offline intent existing only in process memory is vulnerable to loss on termination. The fixture does not explicitly say whether the first draft was acknowledged saved; if it was, loss breaches the requirement, and if it was not, the UI must not represent it as durably saved. A server-accepted submission with a lost response is an ambiguous outcome. Retrying with a new request ID risks duplicate business submissions; the scenario does not prove a duplicate occurred or establish backend deduplication.

Proposed recovery ownership: the client may durably own draft and pending intent; only the accepting business boundary can establish accepted submission identity and prevent duplicate effects. Require its concrete idempotency key scope, expiry, payload mismatch behavior, authorization isolation, status lookup and atomic effect contract. A stable client ID by itself does not prove exactly-once acceptance. Until a contract is evidenced, an ambiguous result must remain unresolved or be reconciled through an existing authorized workflow; automatic retry with a new identity is unsafe for the stated requirement. Do not add a backend to satisfy this exercise.

For a later authorized implementation, inspect the actual iOS workspace/schemes/deployment targets and Android modules/variants/SDK levels before selecting commands or APIs. iOS scene restoration differs from durable draft persistence; Android configuration/activity recreation differs from process death. Background completion cannot be promised independently of OS policy. Use current primary platform documentation for concrete API choices; no network was authorized here, so no concrete API/entitlement command is asserted.

The future evidence matrix should cover source review, meaningful persistence/operation-contract checks, named simulator/emulator lifecycle scenarios, real-device interruption/network/permission checks, and separate archive/signing/beta/store evidence when distribution is requested. Include interrupted persistence, lost response after acceptance, duplicate retry, restart, account isolation and conflict cases. All these layers remain unavailable, with zero product tests executed.
