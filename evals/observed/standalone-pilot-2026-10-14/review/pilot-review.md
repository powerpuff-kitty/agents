## Finding P2: evidence runner succeeds when a required subcommand fails

Location: `../pilot/run_gates.py:44` through the final result-writing/print at `:57`. The runner records `result.returncode` but neither raises nor returns a nonzero process status for failed gates. A caller using the documented `python3 -B run_gates.py` exit code can therefore accept a failed check.

Reproduction: `pilot-repro/runner-failure/run_gates_failure_copy.py` is a disposable copy with only ROOT relocated for read-only Git identity and its command list replaced with the harmless `/usr/bin/false`. The original execution/recording/aggregation code is unchanged. The command returns **1**, `logs/gate-results.json` records **1**, but the runner process returns **0**. See `pilot-repro/runner-failure/reproduction.json`, stdout/stderr and copied source. This is a controlled runner-failure input, not a claim that a project gate actually failed.

Counterevidence: every original `../pilot/logs/gate-results.json` entry is zero, matching raw logs and the independently rerun gates. The report supplies per-command results rather than relying only on the runner status. This defect does **not** invalidate those actual passes and is outside the shipped project source. Correction: retain all logs/identity records, then exit nonzero if any gate fails; add a meaningful failing-subcommand regression. Recheck this exact negative case and the passing case. No original script was changed.
