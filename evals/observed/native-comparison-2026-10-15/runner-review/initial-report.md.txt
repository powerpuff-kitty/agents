## Findings

1. **P1 — Time budget can expire before prompting, yet inference is still submitted.** `execute` starts its clock at line 316 but first tests it at lines 365–370, after the prompt request and a complete recursive capture. Host readiness, inventory retries, session creation, and the prompt request have no remaining-budget check. Each capture can perform many separately bounded requests, so an active inference may also run substantially past the requested timeout before the next check. The offline fake host advanced the monotonic clock to 10 seconds during readiness with a 1-second budget; `/api/session/root/prompt` was nevertheless submitted at second 10 and the result was subsequently `timed_out`. This is a definite admission-bound failure even without claiming a hard invoice cap. Check the deadline before prompting and carry the remaining deadline through I/O, polling, and cleanup; test the exhausted-preflight path.

2. **P1 — Active default-agent instructions are not verified or retained.** `verify_inventory` (lines 165–184) validates staged custom agents/skills, and only the `steps` field of built-in `build`. `execute` validates the resolved agent ID only for named-agent mode (lines 345–353). Ordinary and skill mode can therefore resolve any ambient default agent, including one with a different step limit and unknown system instructions. The probe returned an `ambient-agent` with 99 steps and an unverified system body; the preflight retained only the two staged custom agent identities and still submitted the prompt. Even the expected built-in `build` system body is not included in the inventory identity. Verify the actual resolved active agent, record its loaded instruction identity and bounds, and state the remaining limits around host-injected/project/global instructions. A custom-catalog inventory alone is not the active prompt identity.

3. **P1 — Partial prior attempts are overwritten and simultaneous attempts are unclaimed.** Lines 308–309 reject only an existing final `result.json`. A killed/crashed process can already have `preflight.json`, `submitted-prompt.json`, `sessions.json`, and `messages.json` but no result. The next invocation writes those same paths at lines 354, 358, 362–363 and 388–389. The probe seeded prior-attempt preflight/prompt records without a result; both were overwritten. There is also no exclusive attempt marker/lock to prevent two invocations from passing the guard and starting paid calls for one roster slot. Preserve attempts in separate exclusively created directories, or fail closed on any existing execution evidence and require an explicit new attempt identity. Final-result preservation does not satisfy preservation of all attempted executions.

4. **P2 — Staging drift is omitted from preflight and deleting Git metadata passes the preservation check.** `snapshot` excludes `.git` (lines 53–54); preflight compares only that snapshot and prompt identity (lines 319–323), ignoring captured `git-before.json`. Resetting the staged `pricing.py` entry left the snapshot match true while changing the captured staged hash. After removing the disposable `.git`, `invariant_checks` (lines 289–291) returned both `source_scope_preserved: true` and `staging_entries_preserved: true` because `git_state(project) is None` is accepted unconditionally. Require the expected Git-repository presence and captured staged-entry identity before inference and after execution. Preserve the distinction between expected absence and disappearance. Actual index bytes are retained but are not checked; staged-entry equality alone does not prove all index metadata remained unchanged.

5. **P2 — Cleanup does not cover owned descendant processes.** `Host.close` (lines 224–230) terminates/kills only the server PID; the server is not started in an owned process group/session (lines 202–203). Session interrupts may help during normal host operation but are not a process-ownership cleanup boundary when a host is unresponsive or exits first. An actual local parent/child probe passed the parent Popen object to `Host.close`: the parent exited, while its owned sleeping child remained alive. The probe explicitly terminated that known child afterward. Establish and bound cleanup of the owned process tree/group without targeting unrelated host processes. This test establishes the runner's gap, not a claim that OpenCode always leaves its children behind.

## Confirmed strengths and limits

The runner and directly imported helpers use the Python standard library. Preparation contains no Host construction or provider call. The offline synthetic preparation produced nine roster entries (three cases × three modes), nine explicit `not_run` report rows, and one identical workspace snapshot hash per case across modes. `report` preserves missing slots; task acceptance remains separately marked `needs_independent_review`/`unverified`. Explicit host/model/positive finite time/reported-cost options are required by the CLI. Resolved project/model checks occur before prompting, and custom staged skill/agent content is checked against host inventory. Descendant sessions are traversed and usage is summed when API fields are present. Reported cost is expressly a host-reported interrupt threshold with unknown hidden calls and possible overshoot, not complete billing.

No actual OpenCode API compatibility, native permission enforcement, native child-session discovery, tool trace completeness, real usage accounting, compiler behavior, or model outcome was established by this review. Mock responses demonstrate runner control flow only. Artifact invariants and host `succeeded` do not establish task semantic correctness. Native trial evidence remains pending a later followup. A full repository build/test suite was not run because this was a read-only focused runner review, not a repository modification.
