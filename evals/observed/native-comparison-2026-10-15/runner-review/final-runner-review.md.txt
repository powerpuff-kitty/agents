## Remaining concrete limits

1. **P2 — Absolute request-body deadline remains unenforced.** Host.request computes the remaining time before `opener.open` and uses it as an I/O timeout, then reads the response body without an absolute deadline/watchdog. The current frozen-source offline probe returned successfully after advancing time by 10 seconds during read with a 1-second deadline; only the next request was refused. Evidence: `final-runner/deadline-probe.json`. This does not involve a socket or provider. A socket operation timeout is not proof of a total-body wall-clock cutoff for a continuing slow stream. Startup/version checking, cleanup and invariant tests also have separate allowances. This remains a blocking qualification for any claim of a hard end-to-end time bound; it does not invalidate the actual recorded bounded executions. Describe the implementation as request/deadline checks with best-effort interruption and separate cleanup/check overhead unless a true whole-operation deadline is enforced.

2. **P2 — Strict read-only index preservation is not the checked invariant.** Final staging checks compare `git ls-files --stage` hashes, not captured `index_bytes_sha256`. The host environment does not set `GIT_OPTIONAL_LOCKS=0` for its allowed Git status commands (only the runner's own git_state helper does). The separate read-only retry supplies concrete evidence: its index-byte hash changes while `staging_entries_preserved` is true. Parsing retained original07 index bytes (matching retry's before hash) and retry's final index shows only tracked-file ctime/inode stat-cache fields plus checksum changed; staged object IDs, modes and flags are unchanged. Thus semantic staging preservation is supported, but literal index immutability is not. This blocks certifying the retry's explicit no-index-edit constraint under a strict interpretation. Preventing optional index refresh and/or checking/reporting the expected invariant explicitly would avoid conflating the two. No deliberate staging edit is alleged.

3. **Instruction/accounting visibility is still narrower than full inference identity.** The exposed built-in `build` fingerprint can be the empty-string digest when the registered system field is absent; it is not a verified complete provider prompt. Requested/resolved primary IDs, staged custom bodies and actual skill text are evidenced, but ambient/host-injected prompt contributions and unexposed auxiliary usage remain unknown. Numeric session/message reconciliation does not establish invoice completeness, especially with usage-free partial/aborted assistant rows. Existing report disclaimers correctly limit these claims; do not remove them.
