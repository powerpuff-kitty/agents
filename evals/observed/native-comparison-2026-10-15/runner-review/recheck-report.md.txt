## Remaining findings and evidence limits

1. **P2 — Registered `build` system fingerprint does not establish complete loaded-instruction identity.** `verify_inventory` line 185 hashes `str(loaded_agents['build'].get('system', ''))`; absent, null, and actual body states are not retained as distinct raw registry evidence. A missing `system` field is accepted and recorded as SHA-256 of the empty string. This was reproduced: a valid controlled run with no `build.system` field was collected and preflight retained `e3b0c442...`, 12 steps, and the stated complete-provider-prompt limit. Unlike staged custom profiles, no expected built-in instruction body is compared. The revised evidence is sufficient to support “session requested and resolved agent ID build with registered step bound 12 and recorded registry fingerprint,” when actual host records agree. It is not sufficient to claim all active instructions were verified, that no ambient instruction/override contributed, or that the original built-in body was authenticated. The complete provider prompt is expressly unavailable. Preserve that limit in trial reporting; recording the actual registry field presence/type/body or a host-native identity flag where available would make the fingerprint easier to audit.

2. **P2 — Request deadline remains an I/O admission/timeout control, not an absolute request-body wall-clock cutoff.** `Host.request` lines 212–223 checks the remaining time before `opener.open`, passes it as the socket timeout, then performs `response.read(20_000_001)` without a deadline recheck or independent stop during the body read. A fake response that advanced the clock by 10 seconds with a 1-second budget returned `{}` successfully; the next request was refused. The mock proves this control-flow behavior, not that OpenCode actually streams slowly. In real socket terms a timeout on blocking I/O is not a proof of an absolute whole-body deadline, particularly for a response that continues delivering data. Version checking also has its independent 10-second timeout, and cleanup/invariant checks have separate bounded allowances. Therefore describe `--timeout` as an inference deadline checked around requests with best-effort interruption and disclosed cleanup/check overhead; do not claim a hard total process-runtime bound from this implementation. The original paid-call admission after expired preflight is fixed.

## Controlled-primary claim and pre-prompt evidence

This experiment deliberately controls the primary role: ordinary and skill modes explicitly request `build`; named-agent mode explicitly requests the case's custom role. The `skill` arm additionally requests a named installed skill. It does not measure ambient automatic selection of the primary agent. Child selection and actual skill calls still require retained native activity evidence; passing an explicit `skills` request is not itself proof of invocation.

For this narrower claim, the source now produces the useful pre-prompt chain: frozen roster/model/fixture/prompt hashes; preserved before snapshot and Git state; explicit requested agent/model/project; resolved project/model/agent check; verified staged skill path/body and custom agent body/step bound; registered `build` fingerprint/step bound with a complete-prompt limit; preflight session record; intended submitted prompt. The explicit requested agent is not separately repeated in `preflight.json`, but is derivable from the frozen entry and runner implementation and is checked against the recorded resolved session. A deadline may expire after `submitted-prompt.json` is written but before the request: that filename is an intended request record, and actual submission/completion needs the outcome/error plus native messages.

Registered built-in identity is narrower than a fully observed provider prompt. No configuration inspection was performed to infer absent ambient contributions. No API/permission compatibility or actual model behavior was established. The fixed roster and separate `needs_independent_review` task acceptance remain useful boundaries. Artifact checks and host `succeeded` remain insufficient for semantic task acceptance.
